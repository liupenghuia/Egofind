# Product Request Template

这是非技术产品负责人提交需求的默认入口。产品负责人只需要描述目标和用户结果，不需要指定代码方案。

## 默认输入

```text
请帮我完成这个产品需求：

[用自己的话描述需求]

我的目标是：
[我希望用户最终能做到什么]
```

## 顺序完成指令

当产品负责人发送 **「顺序完成」** 或 **「交付」** 时，按 **`docs/delivery-pipeline.md`** 自动串起各 Agent，**不必**再逐条喊 `UI设计` / `架构` / `小程序`。

推荐输入：

```text
顺序完成：

[用自己的话描述需求]

我的目标是：
[希望用户最终能做到什么]
```

### 自动相位（默认）

1. **Product Agent** 整理需求、范围、用户流程、验收标准，并判定是否需要 UI / 后端 / 小程序 / 管理端。
2. 发现重要产品取舍时，用非技术语言说明，并只询问必要决策；**无取舍则不中断**。
3. **UI Design Agent 自动启动**（当需要小程序或 Web 的可见界面时）：根据产品结论写 `docs/ui/specs/*.md`，默认在流水线中自动 `Approved`。  
   - 写 `UI 需我确认` → UI 相位后暂停等你点头。  
   - 写 `跳过 UI 设计` → 跳过本相位。  
   - 纯后端/无界面 → 自动 `ui_spec: N/A`。
4. **Architect Agent 自动启动**：结合产品范围与 UI Spec，设计边界、数据模型、API、权限、隐私和回滚。
5. **开发 Agent 自动启动**：按依赖实现后端 → 小程序 / 管理端；契约稳定后方可并行。
6. 补充正常流程、加载、空数据、错误、重试、权限、登录失效和隐私处理。
7. 运行适用的单元、集成、客户端和交付验证（含 `ruby scripts/deliver.rb` 若已有 task）。
8. **Test Agent** 独立对照验收标准（含 UI Spec 验收条），不替实现 Agent 隐藏失败。
9. 对失败项创建或更新 issue，由所属 Agent 修复，再由 Test Agent 独立复测。
10. 未验证的内容必须标记为待验证、Blocked 或未完成，不得报告为完成。
11. 最终用简单语言汇报：已完成什么、尚未完成什么、是否可以体验、产品负责人下一步只需做什么。

> 真相源：`docs/delivery-pipeline.md`。与本文冲突时以 pipeline 文档为准。

## 固定约束

- 不擅自扩大需求或改变用户目标。
- 不重写无关模块，不破坏现有正常功能。
- 不确定的产品行为先记录为假设或未知，不把技术猜测当成产品决定。
- 需要产品取舍时只提出最小必要问题，并说明各选项对用户和进度的影响。
- 生产发布、真实用户数据、密钥、付费外部服务、不可逆操作和敏感权限必须先获得产品负责人的明确确认。
- 发现后续优化时建立独立记录，不在当前任务中顺手扩大范围。

## 产品负责人关注点

产品负责人只需要确认：

- 目标用户是否正确。
- 用户最终是否能完成目标。
- 哪些功能必须现在完成。
- 哪些功能可以后续优化。
- 验收结果是否符合预期。

产品负责人不需要决定：

- 使用什么框架或数据库。
- API 如何实现。
- 文件如何拆分。
- 测试如何编写。

这些内容由 UI Design、Architect、Backend、Frontend/Mini-App 和 Test Agent 在既定边界内负责。

产品负责人默认一句话即可驱动整条链：

```text
顺序完成：……（需求描述）
```
