## 定位

本文件是实现类工作的**硬前提**。  
用户要的是可长期演进的高质量代码，不是门禁报表、任务状态机仪式，或“Blocked / DevTools 不可用”类过程说明。

除非用户**明确要求**交付编排、任务状态推进、平台验收或流程门禁，否则默认：

- **不**主动管理 task/issue 状态机 / 门禁通过与否  
- **不**把时间花在解释为什么无法做微信 DevTools、真机、浏览器人工验收  
- **只**围绕需求写出高质量、可维护、可扩展、健壮的代码，并用可运行的本地验证证明行为正确

## 落码前检查清单（必须完成，再写代码）

### 1. 意图与验收

- [ ] 用户本轮明确要什么（行为结果，不是文件列表）  
- [ ] 可观察验收点 ≤ 3 个主目标；邻近优化记 follow-up，不塞进本轮  
- [ ] 与 `requirements.md`、task、OpenAPI/现有行为冲突时，以**用户最新意图 + 既有契约**对齐  

### 2. 现状基线（短基线，禁止全仓漫游）

- [ ] 已读将改模块及其直接依赖的现有模式  
- [ ] 单一事实来源：API、域规则（`domain-rules.md`）、客户端状态归属  
- [ ] 不应触碰的范围已标出  

**短基线应包含：** 当前任务与验收、本轮意图变化、已确认可用行为、允许/禁止改动范围、最近验证命令与未解决风险。

### 3. 设计边界

- [ ] 展示 / 编排 / 域规则 / 数据访问 / 平台适配分层清楚  
- [ ] 复用现有 client、域模块、工具；无第二消费者不抽共享层  
- [ ] 契约变更有意识；内层不依赖外层 UI/平台  

### 4. 健壮性

- [ ] 非法输入、权限、空数据、重复提交、网络失败有明确行为  
- [ ] 错误不吞；鉴权在服务端  
- [ ] 主路径 + 至少 1 条关键失败路径可本地验证  

### 5. 实现纪律

- [ ] 最小 diff；风格一致  
- [ ] 改完跑最近模块检查；失败先修根因

## 迭代与变更纪律（原 iterative 文档）

1. 先判断：修复 / 需求实现 / 后续优化；无授权不把优化改成大重构。  
2. 修改前列出最多 **3** 个可观察结果，且可验证。  
3. 先用现有模式；只有无法满足验收时才加抽象。  
4. 单轮一个主行为主题；邻近问题记 follow-up。  
5. 保留用户已有修改；不确定时最小合并，不整文件重写。  
6. 未确认视觉偏好用保守改动，标「待优化」。  

### 快速验证环

1. 读目标文件与直接依赖  
2. 最小实现  
3. 文件级检查 / 单测  
4. 任务级 `deliver.rb` 或最近等价命令  
5. 检查 diff 未越界  
6. 仅用户要求交付时才改 task 状态  

测试失败只修当前根因。缺环境/人闸不假装通过。

### 交接格式（实现轮）

- 已完成的可观察行为  
- 精确变更文件  
- 精确命令与结果  
- 未确认内容及原因  
- 下一轮唯一最高优先级动作  

### 完成边界

满足当前验收即可结束本轮；不要求一次做到最终视觉/架构理想。后续优化用独立 task/issue。

## 质量标准

| 维度 | 要求 |
| --- | --- |
| 正确性 | 行为匹配意图与契约；可复现验证 |
| 可维护 | 5 分钟内找到状态 owner、数据流、失败出口 |
| 可扩展 | 新字段/状态可局部扩展 |
| 健壮 | 异常路径一等公民 |
| 简洁 | 不过度抽象 |
| 一致 | 同问题同模式 |
